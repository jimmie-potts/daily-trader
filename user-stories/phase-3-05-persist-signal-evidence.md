# P3-05: Persist Signal Evaluations and Evidence

## User Story

As an auditor, I want every signal evaluation and its evidence stored durably so that fired, non-fired, suppressed, superseded, and retracted results remain explainable and reproducible.

## Acceptance Criteria

- New checksum-protected migrations add the immutable append-only canonical-bar revision journal, signal runs, globally identified append-only evaluations and occurrences, role-ordered evidence links, run-scoped evaluation/occurrence associations and transitions, source-namespaced durable run cursors, and deterministic run-scoped latest-revision projections without modifying the applied Phase 2 migration.
- Each canonical revision stores its commit-ordered position, logical bar key, previous and new canonical event IDs, `insert` or `replace` operation, separate arrival/gap metadata, market-event schema, and operational `journaledAt` transaction timestamp. While live signal capture is active, the repository selects the prior canonical event under its existing series lock, changes the canonical row, and inserts the revision in the same transaction only when canonical state changed. Journal failure rolls back the PostgreSQL ledger, canonical, and journal changes; the Redis handler fails before acknowledgment, leaving its entry pending and recoverable. Position allocation updates one locked application-owned counter row held through commit, intentionally serializing revision-producing canonical commits across the approved AAPL/SPY scope so rollback and inverted transaction completion cannot create an invisible predecessor or false contiguous gap; `GENERATED ... IDENTITY` alone is insufficient. Duplicates, losing replacements, noncanonical events, and pre-cutover changes insert no run-owned revision.
- Signal runs have explicit `live_journal` or `replay_schedule` source kind; pending, active, closing, completed, or failed state; source-specific cursor namespace; start and optional frozen stop watermark; effective scope; source provenance; claim-fencing state; and expected ordered membership when known. They persist the complete named P3-01 semantic identity set; replay additionally persists catalog, schedule, and manifest versions/checksums.
- Each run stores its ordered cutover warm-up event associations, scalar journal watermark, and per-instrument first evaluation-bar boundary so restart can reconstruct the same bootstrap even if global canonical rows later change. Pre-cutover evidence remains distinguishable from evaluated run input.
- Globally deterministic evaluations and occurrences associate many-to-many with live or replay runs. Each run association owns its ordered predecessor, triggering revision, supersession/retraction meaning, and latest-revision membership; those transition relationships are never stored as one global chain. Market-data ingestion session, NYSE exchange session/date, signal run, and recording checksum remain distinct provenance concepts rather than one overloaded session identifier.
- Each evaluation stores its immutable versioned feature result as a canonical payload plus normalized role-ordered evidence links. Mutable in-memory feature state and optional performance checkpoints are never audit authority.
- Storage retains instrument, direction when applicable, canonical observation/knowledge-as-of context and separate operational timestamps, on-time or retrospective mode, outcome and bounded reason, explanatory invalidation condition, source/feed/entitlement, shared window bounds/count, evidence role and ordinal, every evidence event ID, and all exact observed/reference/threshold values with currency or units. The run association separately retains the triggering revision ID and commit-ordered position as transition provenance.
- PostgreSQL exact values use `NUMERIC` with text-only application codecs. No persisted arithmetic value passes through JavaScript `number`, and operation-specific rounding metadata is retained wherever the accepted policy rounds.
- Deterministic evaluation and occurrence IDs plus database uniqueness make duplicate delivery, retry, and restart idempotent. One feature-result identity cannot produce more than one global evaluation or occurrence, and each run-scoped latest-revision projection has one row per definition, configuration, instrument, and evaluation bar.
- Any changed deterministic feature-result identity—including evaluation-bar revision, eligibility/knowledge-as-of context, or ordered prior evidence—associates a new or already-known global evaluation and appends a run-scoped transition to the prior latest revision even when the outcome is unchanged. Within that run, a prior fired occurrence is retracted only when the replacement no longer fires; fired replacements supersede prior fired evidence. Historical rows, associations, and transitions are never updated in place, deleted, or hidden by the latest-revision projection.
- Run association is idempotent: an already-known global evaluation or occurrence is linked into each replay target in exact target order. Live journal positions and replay target ordinals are distinct cursor types; wrong-source cursor updates and overlapping unfenced claims fail. A run cannot complete merely because global rows already exist; its expected membership, counts, source coverage, and canonical output must all verify. Failed or interrupted runs remain explicitly incomplete and retryable.
- Read interfaces can reconstruct a feature result, explain any historical occurrence, select the deterministic latest evaluation revision for each evaluation bar within one run, list that run's non-superseded and non-retracted fired history, and export canonical run output without returning raw provider frames or secrets. Canonical exports use deterministic target ordinals where ordering is required and exclude global journal positions, database commit/generated timestamps, worker timestamps, fencing values, and run-local generated identifiers.
- Migration ownership is renamed or generalized from `market-data:migrate` before signal migrations are applied; root commands and operating documentation cannot imply that application-wide migrations remain market-data-only.

## Validation

- Integration-test fresh and repeat migrations, revision insertion atomicity, rollback during position allocation, inverted concurrent commit attempts, exact-value round trips, fired/non-fired/suppressed rows, role-ordered evidence, duplicate and concurrent repository calls, every supersession/retraction case, two runs sharing one global evaluation through different predecessor chains, live/replay cursor namespace rejection, overlapping-claim fencing, exact target membership, interrupted-run retry, transaction rollback, database outage, and deterministic run-scoped latest-revision queries against local TimescaleDB.
- Verify that append-only history remains valid for each input order and that equivalent correction orders converge on the same byte-stable latest-revision projection and non-superseded/non-retracted fired set. Intermediate audit rows may differ when the observed canonical-transition history genuinely differs.

## Dependencies

- P3-03 versioned feature snapshots.
- P3-04 signal evaluations and occurrences.

## Out of Scope

Do not delete or compact audit history, create a dashboard source of truth, send alerts, add portfolio or risk state, or introduce broker and execution tables.
