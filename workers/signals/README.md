# Signals worker

This workspace consumes only the committed PostgreSQL canonical-revision journal. It reconstructs feature state from each run's persisted bootstrap plus revision history, evaluates `breakout_plus_volume.v1`, and commits evidence, transitions, latest projections, and the run cursor atomically.

The worker's configuration projection drops provider, Redis, broker, account, and execution configuration before orchestration. It does not connect to Alpaca, Redis, a broker, alerting, AI, portfolio, risk, orders, or execution.

`SIGNAL_MODE=disabled` is the safe default. A normal disabled worker may open PostgreSQL to atomically freeze an active run and drain only its already captured finite journal debt; canonical commits after the disable boundary create no signal debt. The `--once` smoke path opens no service connection. `SIGNAL_MODE=monitor` is the only enabled mode and creates observations only.

On monitor enablement, the repository audits open paper-writer capability rows before it mutates run state. Missing legacy rows, retired or incompatible capabilities, and future-dated heartbeats block cutover; an exact accepted row whose lease expired is treated as an inactive crashed writer. Every active/fresh writer must advertise `daily-trader.market-data.canonical-revision.v1` with the run's frozen freshness threshold and data-quality policy. The current persistence writer is fenced again by a deferred commit-time lease check, so a writer cannot outlive its lease while waiting for the global counter. The repository then captures a consistent AAPL/SPY bootstrap and watermark under fixed-order locks. Same-configuration restart resumes the durable cursor; configuration rollover freezes the old run and transfers future capture to a pending replacement. A genuine journal gap, capacity failure, incompatible writer, or exhausted retry stops safely without dropping revision work.

The worker emits bounded signal metrics for lifecycle and failure state, fixed evaluation outcomes and suppression reasons, backlog/cursor lag, revision age, retries, retrospective work, and in-memory capacity. Feature, evaluation, claim, reconstruction, and drain latency are measured separately with a monotonic clock. Metrics never include run, event, session, or evidence identifiers, evidence payloads, symbols, exception text, or other unbounded labels.

Use the repository root commands for normal operation. `npm run signal:status` reads the selected persisted live run and labels IEX evidence as a single-exchange observation, never a recommendation or position action. The workspace CLI also owns the bounded disable-and-drain operation.

PostgreSQL-backed signal replay uses an isolated `replay_schedule` run and the same evaluation/evidence/transition persistence semantics. `npm run signal:recording:verify` verifies the checked-in fixture without a service connection. After local migrations, `npm run signal:replay` persists or idempotently resumes the target, and `npm run signal:replay:inspect -- <target-id>` renders only that explicitly named replay run. `npm run verify:phase3` owns the credential-free clean-target, existing-state, and interrupted/service-restart matrix.

The worker and replay persistence implementation has unit/static coverage, and the full credential-free verifier passed its Docker/PostgreSQL service, same-configuration restart, configuration-rollover, bounded-disable, clean-target, existing-state, exact interrupted-prefix, and interrupted replay matrix. Phase 3 completed after the separate P2-11 provider smoke observed both approved symbols; the P3-09 implementation note remains the canonical completion record.
